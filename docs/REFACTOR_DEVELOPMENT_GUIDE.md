## 1. 目标与执行约定

本轮重构要把“页面里同时处理请求、HTML 解析、业务规则、缓存和界面状态”的结构，逐步改为职责清楚、边界稳定、便于 AI 持续维护的结构。

核心目标：

1. 按业务域拆分代码，明确界面、业务编排、数据访问、网页协议和本地存储的责任。
2. 抽取确实重复且语义一致的公共能力，减少同一规则在多个页面独立实现。
3. 重构结束时，所有纳入范围的手写 Kotlin 文件物理行数不超过 **250 行**。
4. 保留现有功能、源站协议、数据兼容性和主要交互行为。
5. 让后续修改通常落在某个业务域内，避免修改一个功能就需要重读数千行全局文件。
6. 为 AI 提供可以分批执行、交接、审查和回退的开发流程。

执行期间遵守用户约定：**不开展具体业务测试；全部结构改造完成后，再统一进行实机测试。**

这里的“具体业务测试”包括运行 parser / repository / service 单元测试、业务断言、MockWebServer 场景验证、模拟器功能验证、真实源站流程验证和阶段性实机回归。重构中不以“补测试”替代此约定，也不要求每个阶段人工操作账号。

重构期间仍执行编译、静态检查、代码审查和结构检查。这些检查用于发现引用、类型、职责和文件规模问题，**不能证明业务行为正确**。已有测试保留并按需修正包名、构造方式和导入；可以编译测试源码，但不运行测试、不删除断言以解决编译问题。

本轮是渐进式重构，不是另写一套客户端。每批替换一个明确边界，旧入口可以暂时代理新实现；最终交付前清除迁移代理和旧实现。

## 4. 架构选择

### 4.1 总体方案

先在现有 `:app` 内完成**按业务域组织的分层架构**。目录边界稳定后，未来才考虑 Gradle 多模块化。

页面采用 Route / ViewModel / UiState / Screen 的分工；业务复用或复杂编排使用 UseCase；数据入口使用 Repository；源站请求、HTML 解析、本地存储作为 repository 内部实现。

Android 官方建议界面由状态驱动、ViewModel 接收操作并提供状态，以及按复杂度选择业务层；本项目据此使用单向状态流，并按需增加 UseCase，而不是为每个读取操作增加一层类。[Android 架构建议](https://developer.android.com/topic/architecture/recommendations)

本文另外约定：repository 接口放在 `domain/<业务>/`，实现放在 `data/<业务>/`。这是本项目选择的依赖边界，不是声称所有 Android 项目都必须采用相同目录。

### 4.2 调用链与代码依赖

业务调用链：

```text
用户操作
  → Route / ViewModel
  → UseCase（确有业务编排时）或 Repository 接口
  → Repository 实现
  → RemoteSource / LocalStore
  → ForumTransport / HTML Parser / 平台实现
  → 业务模型
  → UiState
  → Screen
```

代码依赖规则：

```text
ui       → domain、core 的纯模型与契约
domain   → core 的纯模型与契约
data     → domain、core
platform → 相关纯契约及 Android / WebView / 文件等平台 API
di       → 各层实现，仅负责装配
```

这是“调用链”和“依赖关系”的两个视角：domain 调用 repository 接口，实际执行者来自 data；domain 无需 import data 实现。

强制规则：

1. Screen 不依赖 `LsbClient`、OkHttp、Jsoup、源站 parser 或 SharedPreferences。
2. ViewModel 不直接处理 HTML、Cookie、CSRF 和 HTTP 表单。
3. domain 不依赖 Android、Compose、Jsoup、OkHttp 或 data / ui 实现。
4. data 不依赖 ui，不操作导航、Toast、Compose 状态或 UI 缓存。
5. 平台层可使用 Android 类型，但不得绕过 repository 执行论坛业务流程。
6. 业务域之间优先通过窄接口协作，禁止通过另一个域的 ViewModel 复用业务。
7. 构造依赖由 DI 层提供，页面不自行创建网络和存储实例。

正文排版解析是一个明确例外：输出含 `AnnotatedString`、颜色和对齐等表现类型的 parser 放在 `ui/common/content/`，它解析已获取的正文片段，不负责识别论坛页面、登录状态或提交表单。

## 6. 250 行约束与拆分规范

### 6.1 统计口径

- 硬限制为 **每个手写 `.kt` 和 `.kts` 文件 ≤250 个物理行**。
- 包含 package、import、注释、空行、长字符串所占物理行和文件末尾内容。
- 覆盖 main、debug、release、test、androidTest，以及根工程和各模块的手写 Kotlin 构建脚本。
- 排除 Gradle / IDE 缓存、build 输出、第三方原样代码和真正自动生成的文件；排除项须逐项说明。
- 当前嵌套同名目录不属于本轮根工程，不应在检查时被误认为第二个 source set。
- 文档、HTML 资源、图片、JSON 夹具不适用 250 行，但不能把 Kotlin 逻辑搬入脚本或资源文件规避限制。
- 不以有效代码行、压缩行或删除注释替代物理行数。

建议新文件保持 120～220 行，为后续正常维护留余量。250 是上限，不是每个文件都要填满的目标。

### 6.2 渐进收敛

第一次扫描生成历史超限清单，记录路径、行数、归属业务域和计划批次。迁移期间允许清单内尚未处理的旧文件暂时超限，但应遵守：

1. 新增文件立即满足限制。
2. 新增业务逻辑不得继续进入超限旧文件；旧文件只保留必要迁移接线。
3. 每批完成时，该批选定的超限文件必须降至 250 行以内或被删除。
4. 如一个大文件需要多个批次拆分，提前定义每批职责和应减少的超限量，不临时扩大豁免。
5. 修改既有豁免、放宽上限、排除新增手写文件，均不算完成任务。
6. 最终历史清单清零，最终检查对整个范围严格执行。

历史清单用于显示剩余工作，不能作为永久 baseline 隐藏违规。

### 6.3 如何拆分

按职责拆：模型、解析、请求、业务规则、状态、展示组件和平台适配。先标出状态读写关系与调用图，再决定文件边界。

不接受下列形式：

- `TopicScreenPart1.kt`、`Part2.kt` 等只按行号切割。
- 把全部私有函数改成 public，以便随意互相调用。
- 一个 controller 持有原页面全部状态，再拆十几个只访问它的文件。
- 用扩展函数分散同一个巨型类的实现，类仍承担全部职责。
- 合并多条语句、压缩 import / 注释、把多行逻辑写成一行。
- 为每个 10 行函数单独造一个类，导致理解一次操作要跳转大量文件。

普通函数建议控制在约 60 行以内，复杂 Composable 建议约 80 行以内；这是审查提示，不是通过机械抽取必须达到的第二条硬限制。若无法简化，应解释其完整状态或算法边界，仍需满足单文件限制。

## 8. HTML 协议隔离

### 8.1 网页适配链

```text
HTTP Response
  → 响应分类（正常页 / 登录页 / 验证页 / 源站错误）
  → 对应页面 parser
  → 网页解析模型与表单描述
  → Repository 转换为领域模型
  → ViewModel 映射为 UiState
```

状态码 200 不代表业务成功。登录跳转、验证页、权限错误、表单错误和正常空列表须能区分。不得把未识别的页面转成“空数据成功”，也不得仅凭跳转或页面标题判定所有写操作成功。

`Response` 至少保留现有调用需要的状态码、最终 URL、必要响应头、正文及会话版本。解析时使用最终页面 URL 作为相对链接依据；源站内外地址解析和业务导航分开。

### 8.2 parser 分工

- parser 接收 HTML / Document 和必要上下文，返回数据，不发送网络请求。
- 各业务 parser 独立管理选择器；同一个字段的选择器及容错路径只在一个位置定义。
- `TopicPageParser` 负责编排，标题、面板、回复、分页和表单各自独立。
- 必填身份字段缺失应返回明确解析失败；真正可选的字段才有默认值。
- 数字格式、相对时间、ID 和地址清洗先保留已有兼容行为，再集中重复逻辑。
- 不要求每个模型增加网页模型和领域模型两份。结构相同且语义稳定时可共享纯模型；仅在协议细节需要隔离时映射。
- parser 不能返回 Jsoup 节点让 UI 继续查询，不能把 CSS 选择器放进 UiState。

### 8.3 DOM 修改与解析顺序

当前 `parseTopicPage` 中，楼层正文清洗会移除抽奖、虚拟卡等面板节点。必须先读取这些面板，再执行会消费节点的楼层解析。

迁移顺序：

1. 先记录当前各模块读取和删除的节点。
2. 第一批仅拆出函数，保留原调用顺序和共享 Document 行为。
3. 后续把清洗限定在正文节点副本，减少跨 parser 的隐式影响。
4. 每个 parser 标注是否修改输入；新 parser 默认不得修改共享 Document。
5. 对必须继续保持顺序的路径，在编排处写出原因。

Jsoup 的节点删除会修改树，clone 可以用于生成独立副本；但复制范围和额外开销需由本项目评估，不能为消除顺序依赖对整份长帖无限复制。[Jsoup Element 文档](https://jsoup.org/apidocs/org/jsoup/nodes/Element)

由于本轮不跑业务测试，不能声称改用副本后解析结果已经等价。每次改变 DOM 修改方式都应登记最终实机验收场景。

### 8.4 正文表现解析

`Components.kt` 中正文 block 模型已经含表现类型，缓存也依赖颜色和图片合并选项。将其拆为：

- block / table 模型；
- HTML block 分派及节点处理；
- inline 富文本处理；
- 普通文本、代码、表格、图片和视频渲染；
- 缓存及其 UI 侧失效入口。

它们继续位于 UI 表现层。保留正文内容、链接颜色、代码背景、图片合并等现有缓存键因素，以及编辑预览不污染正文缓存的行为。不得为了 domain 纯净而同时重新设计富文本中间表示和缓存。

## 9. 表单、会话与网络不变量

### 9.1 动态表单

源站没有完整 REST API，表单本身就是协议。表单适配应保留：action、method、enctype、hidden 字段、重复 name、选中 submit 的 name/value、字段选项、约束和现有编码规则。

请求字段使用 `List<Pair<String, String>>` 或等价的有序多值结构。不能整体转换成 `Map<String, String>`，否则同名 checkbox、数组字段或 multi-select 会丢值。

UI 可使用与框架无关的动态字段描述；CSRF、hidden 原始字段、请求构造等由 data 保管。提交时 UI 提供业务选择或字段输入，repository 用对应源站表单生成请求。

必须保留当前动态表单中 checkbox 与数量字段配对、同名选项分组校验、熔炼数量计算等规则。不要把称号表单、淘帖收录和普通发帖强行合成同一个业务模型。

源站提供表单 action 时应使用解析后的地址，不在 UI 硬编码“猜测的提交接口”。按钮值与权限以源站提供的数据为准。

### 9.2 CSRF 与写操作

- 保留当前各流程获取和刷新的时机，不将所有 token 缓存在全局常量中。
- 对确有 token 失效重试的操作，保留既有门控、次数和重新取表单流程。
- 写操作超时后可能已经生效；不能因为没有收到响应就自动重放。
- 对不确定结果使用可识别状态，例如 `SubmissionOutcomeUnknown`，保留草稿或输入供用户确认。
- 如旧逻辑在提交后重读源站确认结果，则继续保留；本轮不扩大为全部操作额外请求。
- 不用本地状态取反替代源站明确的 `item_add`、`item_remove` 等动作。

### 9.3 会话与验证

将 `Session` 的会话职责迁移到独立账号组件；Cookie 所有权、账号标识、会话版本和恢复过程各有明确负责者。

保留验证串行化和并发等待行为。UI 验证通过窄契约协调，平台实现负责 WebView / Cookie 协作；data 不 import 验证弹窗，不直接保存 Activity 或 Composable 回调。

验证待处理状态应有请求 ID、完成 / 取消语义及超时处理。宿主销毁、退出账号和取消任务时，不能留下永远等待的 Deferred 或持有已销毁 WebView。

账号切换或退出时：取消账号级任务、推进会话版本、清理对应缓存和 pending UI 请求。旧账号请求稍后返回时，依据请求开始时的账号及版本拒绝写入新账号状态。

### 9.4 网络装配

当前 OkHttp、Cronet、DoH、代理、WebView 网络桥接共同构成运行链路。只拆职责，不重新安排未知顺序。

重点保留：

- 请求头拦截器与 Cronet 回退拦截器的顺序。
- Cronet 的安全重放门控，尤其是非幂等写请求。
- Cookie 读取、保存及 WebView 同步方向。
- 登录 GET / POST 的连接池与网络环境关联。
- DoH / 代理变化时连接池、DNS、Cronet、WebView 和会话恢复的失效顺序。
- 图片请求与论坛正文请求在缓存头上的现有区别。

不允许某个 feature 自建不受全局策略管理的 OkHttpClient。不同外部服务确需不同配置时，由网络装配层显式创建，保留原有路由和配置差异。

## 10. Repository、结果与业务编排

### 10.1 Repository 接口

接口面向业务能力，例如 `getTopic`、`search`、`submitReply`、`loadCollections`，而不是暴露 `get(url)`、HTML 或原始 Cookie。

可采用如下边界示例；这是设计示意，不是本轮已添加的代码：

```kotlin
interface TopicRepository {
    suspend fun loadPage(topicId: Long, page: Int): AppResult<TopicPage>
    suspend fun reply(command: ReplyCommand): AppResult<ReplyReceipt>
}

class SourceTopicRepository(
    private val source: TopicRemoteSource,
    private val cache: TopicCache,
) : TopicRepository {
    // 实现中处理源站适配和既有缓存策略。
}
```

读写职责较多时按能力分离接口，不将所有论坛业务集中到一个 `ForumRepository`。不同文件共享内部 source 是允许的，但不能重建新的万能 client。

### 10.2 错误分类

| 错误类别 | 用途 |
| --- | --- |
| NetworkFailure | 连接、超时等传输问题 |
| AuthenticationRequired | 登录失效或跳转登录 |
| VerificationRequired | 已识别的验证流程 |
| PermissionDenied | 源站禁止当前操作 |
| SourceRejected | 源站明确返回业务错误 |
| ParseFailure | 正常业务页面结构无法识别 |
| StorageFailure | 本地读写或导入失败 |
| SubmissionOutcomeUnknown | 写请求可能已提交，结果尚不确定 |

结果模型集中定义，避免同时长期存在三套 Result / Exception / nullable 协议。迁移期间可在边界桥接现有 `LsbException`，但最终不能靠字符串匹配决定所有业务分支。

取消不是业务失败。捕获异常时必须继续传播 `CancellationException`；不能用裸 `runCatching` 或统一 catch 把取消吞掉后继续刷新、提交或更新状态。

用户提示由 UI 根据错误类别生成，必要时使用脱敏后的源站错误文字。调试信息与用户提示分开；不记录密码、Cookie、CSRF、API 密钥、备份凭据或完整私信内容。

### 10.3 UseCase / 协调器

适用于“加载最新表单 → 校验 → 提交 → 确认结果”、屏蔽规则合并与 pending 同步、导出准备、备份导入等多步骤业务。

页面简单读取 repository 不需要 UseCase 包装。已有 service 按真实职责归位，不仅改名。

业务规则只保留一个实现，UI 可以给出提示或控制按钮，但最终授权以源站为准。解析层负责理解源站字段，不负责改变业务规则。

## 11. 页面状态与 Compose 拆分

UI 视觉与通用交互的具体约束见 [UI 分层与公共组件开发规范](UI_DEVELOPMENT_GUIDE.md)，包括公共入口、主题尺寸、共享显示模型和工具、组件接口及渐进迁移规则。该文档补充本节，不改变本文的兼容性与验证安排。

### 11.1 责任分工

| 类型 | 负责 | 禁止承担 |
| --- | --- | --- |
| Route | 依赖取得、生命周期收集、页面导航接线 | HTML 解析、业务请求构造 |
| ViewModel | 页面业务状态、加载、并发和操作协调 | Context 持有、WebView、界面测量 |
| UiState | 明确的页面状态快照 | 网络客户端和可修改 DOM |
| Screen | 布局、展示、输入和操作回调 | 自建 repository、操作全局缓存 |
| 组件 | 局部展示与短生命周期交互 | 偷读整个 Session |
| UI 状态持有者 | 滚动、测量、展开及必要跳转过程 | 代替 repository 管理全部业务 |

业务状态优先由 ViewModel 通过只读 `StateFlow` 暴露，界面发送明确操作。生命周期感知收集按当前依赖能力接入；如使用 `collectAsStateWithLifecycle`，先核对对应 `lifecycle-runtime-compose` 依赖，沿用项目现有 Lifecycle 版本，不顺带升级依赖。[Android 架构建议](https://developer.android.com/topic/architecture/recommendations)

`remember`、`rememberSaveable` 和 `LazyListState` 等 UI 状态不会全部搬入 ViewModel。先确定状态寿命，再决定归属。

### 11.2 状态迁移清单

迁移每个复杂页面前，逐个变量记录：原位置、读取者、写入者、所属账号、生命周期、持久化位置、目标所有者和恢复方式。

| 状态类别 | 典型归属 |
| --- | --- |
| 当前账号和会话版本 | AccountSession |
| 主题与浏览设置 | 对应 SettingsStore |
| 查询结果和加载错误 | 页面 ViewModel |
| tab 返回后保留的列表与页码 | 明确作用域的首页状态 / 缓存 |
| 滚动位置与测量 | UI 状态持有者，必要时存阅读位置 |
| 菜单或对话框短时展开 | 局部 UI 状态 |
| 编辑草稿 | DraftStore + 编辑 ViewModel |
| 待验证请求 | 验证协调契约与宿主状态 |

禁止把全部状态合成几百字段的 `AppUiState`。页面复杂时按加载、编辑、搜索、回复树等相对独立区域拆分，但需要共同保持一致的字段仍在同一次状态更新中提交。

### 11.3 Effect 与状态恢复

移动 Composable 时必须审查 `LaunchedEffect` 的 key、启动次数、取消时机，以及 `rememberSaveable` 的作用域和 key。

路由、tab、topicId、账号切换产生的状态隔离要显式保留。不要因为组件抽出而导致返回后重新加载、重置滚动位置或重复触发提交。

需要保证处理的导航、错误确认和验证结果，应表示为有 ID 的待处理状态并有确认消费过程；短暂视觉提示才使用合适的事件流。不要让关键结果在界面停止收集时悄然丢失。

### 11.4 并发规则

- 搜索等可替换读取：保留既有取消策略，并使用请求标识拒绝过期结果。
- 分页：按查询 / tab / topic 作用域协调；同一页在途去重。
- 刷新与加载更多：明确互斥、替换和合并关系，旧分页结果不能覆盖新刷新。
- 写操作：busy 状态阻止重复点击，必要时串行处理；不能用取消上次任务实现安全去重。
- 主线程处理 UI；网络和磁盘执行在合适的上下文中，不在 Composable 重组时重跑 parser。
- 新的线程切换不能在移动代码时顺手大改；影响时序的调整必须单列记录。

列表使用稳定的业务 key，回复折叠和选中状态使用 postId 等业务身份，不使用当前列表索引作为永久标识。

## 12. 大文件专项拆分

### 12.1 Session

建议拆为：

- `AccountSession`：登录信息、账号版本和退出边界。
- 各域 SettingsStore：设置读写与可观察快照。
- `HomeBrowseState`：tab、列表和返回保留状态。
- `TopicCache`：帖子页缓存、失效及账号作用域。
- `ReadingPositionStore`：阅读位置持久化。
- `SummaryHistoryStore`：AI 总结记录。
- `KeywordFilter` 协调器：规则同步与 pending。
- UI 侧 `AppUiCoordinator`：验证宿主和确需全局的展示协调。

拆分顺序为“抽出一个责任 → 旧 Session 委托 → 迁移调用者 → 删除旧入口”。不能一次删除所有镜像字段而不核对可观察性。

`CardColorOverrides` 由 UI 从主题状态读取；数据清理通过状态 / 版本通知 UI 失效布局缓存，不能保留 data 对 ui 的全限定引用。

最后不要求 Session 保留某个名字。如果完全被明确组件替代，可删除；若仍保留，必须是 ≤250 行的窄协调入口，而不是另一种聚合容器。

### 12.2 HtmlParser

按首页 / 板块、主题、用户、通知、私信、签到、身份、邀请、称号、举报等业务拆分。

主题详情拆出标题 / 元信息、抽奖、虚拟卡、申精、投票、回复、收藏及回复验证等子解析器，由 `TopicPageParser` 保留明确编排。

拆迁初期保留 `HtmlParser` 代理入口，逐域迁移调用者；最后删除聚合入口和仍依赖其嵌套模型的代码。分页、地址和相同文本规则单独共享，不建立新的 1,000 行 `ParserUtils`。

### 12.3 TopicScreen

先列清当前加载、跳页、全量加载、全文搜索、楼层跳转、排序和折叠之间的状态依赖。

拆分组建议：

| 组 | 目标职责 |
| --- | --- |
| Route / Screen | 页面接线与顶层布局 |
| TopicViewModel | 页面协调，持有细分协作者 |
| TopicLoader | 页面加载、远端分页和合并 |
| ReplyTreeController | 回复树、排序、折叠和显示身份 |
| FloorJumpState | 展开、换页、等待布局、定位与高亮 |
| TopicSearchState | 全文搜索、匹配和定位请求 |
| 互动组件 | 投票、抽奖、虚拟卡和收录 |
| 编辑 / 回复组件 | 文本、上传、预览和提交状态 |
| 详情展示 | 标题、作者、正文、回复项和工具栏 |
| 导出 / 总结接线 | 调用独立领域能力并展示结果 |

楼层跳转目前包含等待重组后再次推进的过程，不能分别抽几个 effect 就认为拆完。先整体保留状态机，再将步骤表达为“准备数据 → 展开祖先 → 切换显示页 → 等待目标布局 → 滚动 → 高亮 → 完成”。

跨远端分页、本地显示分页和回复树索引分别建模，不以一个 `page` 字段表示三种页码。`TopicViewModel` 超限时继续按加载、搜索、回复等职责组合，禁止用多个 extension 文件隐藏体积。

### 12.4 HomeScreen

分离首页分类状态、列表请求、筛选、侧栏、列表布局、抽屉和滚动恢复。

保持每个 tab 的筛选、页码、缓存、待合并新帖和滚动身份。返回帖子页后恢复状态、点击已选 tab 刷新、有限分页与无限滚动的规则分别记录。

移动 `rememberSaveable` 前明确其原作用域；提取组件不能改变用户从帖子返回时的页面寿命。

### 12.5 NewTopicScreen

拆为编辑 UiState、草稿 store、表单初始化、正文编辑组件、版块选择、抽奖字段、虚拟卡字段、提交编排。

普通发帖和编辑帖保留不同入口及源站表单语义。切换版块、上传图片、验证码失败和提交结果未知时保留用户输入，不自动重复提交。

### 12.6 Settings 与 MiscScreens

`AppSettingsScreen` 按设置域拆页，每页由状态、布局和组件构成；备份、WebDAV、网络与数据清理不放回 UI 文件。

`MiscScreens` 先按独立业务页面拆出，再逐页下沉请求。称号动态表单作为同域公共组件，通知与私信独立处理。不要用“misc”或“other”作为新架构的永久业务域。

### 12.7 Components、导航与媒体

公共组件按语义命名，只有实际跨页面共用的才放 `ui/common`。业务特有组件留在自己的 feature。

导航图按账号、阅读、社区工具和设置等现有目的地分组注册。底栏、玻璃底栏和平板导航共享目的地定义，串行导航协调器和恢复语义保留。

视频、图片、导出按状态、渲染、缓存与平台生命周期分离，不能因移文件导致 WebView、Bitmap、流或文件句柄失去清理路径。

## 13. 本地存储、设置与缓存

### 13.1 先建立存储清单

每项记录：存储文件、key / 路径、类型、默认值、读写者、账号作用域、备份字段、重置类别和目标所有者。真实 key 数量实施时重新扫描，不直接采用旧文档的历史数字。

保留 SharedPreferences 格式，统一每项数据的唯一写入者。多个 store 可以使用同一个存储文件，但不能分别维护同一 key 的相互竞争镜像。

### 13.2 可观察设置

设置写入、内存快照和 UI 通知由对应 store 统一处理。先将旧写入路径纳入唯一所有者，再移除 Session 的镜像，防止两处值不同步。

核对每个设置的读取、保存、首次加载、重置、导入、备份、账号切换和 UI 生效路径。主题即改即生效与网络配置需失效后生效，不共用错误的触发规则。

### 13.3 数据兼容

不能改名后“读不到旧数据就恢复默认”。如确有不可避免的格式变化，单独定义版本、兼容读取、失败保留旧数据和迁移记录，并列入最终升级实机测试。

备份导入应保留当前校验与生效顺序，不因拆文件而在部分读取成功时提前清空旧数据。Android URI 权限、分享 FileProvider、导出文件名和文件可访问性保持原行为。

### 13.4 缓存责任

| 缓存 | 必须明确 |
| --- | --- |
| 帖子页 | topic、源站页、账号 / 权限范围和失效触发 |
| 首页 | 分类、排序、账号、筛选与刷新关系 |
| 搜索 | 规范化 query、scope、sort、page 和账号 |
| 正文渲染 | 正文与主题 / 图片合并选项 |
| 头像 / 图片 | URL、在途去重、容量与网络策略 |
| AI 总结 | 记录身份、对应帖子与现有保存规则 |

先保留当前容量、TTL 和失效规则，不用“统一缓存管理器”替代全部差异。缺失的账号隔离问题先登记；为新边界必需的隔离修复单独说明，避免隐式改行为。

## 14. 依赖装配与可见性

使用手工 DI，沿用现有技术栈。`AppContainer` 是装配入口，超过 250 行时按网络、账号和业务域分 provider，而不是把所有创建过程放进巨型容器。

明确组件作用域：网络和设置为应用级，账号缓存为账号级，页面 ViewModel 为导航页面级，WebView 和滚动状态为 UI 生命周期级。

用 ApplicationContext 创建长期组件。Activity、NavController、WebView、View 或 Composable 回调不进入应用级单例。

默认 `private` / `internal`。移文件导致 private 不可访问时，只扩大到完成协作所需范围。禁止为拆分把所有模型、状态 setter 和 helper 全部公开。

跨 feature 公共契约不要包含另一个 feature 的 UI 类型。确需共享状态时，通过明确的状态接口、业务模型或现有事件含义协调。

## 15. 实施阶段与批次验收

下面顺序考虑了本轮不做中途业务验证的约束。高耦合页面后置，但最终不遗漏 250 行以内文件中的跨层问题。

| 阶段 | 主要工作 | 阶段出口 |
| --- | --- | --- |
| 0 基线 | 确认根工程、版本基线、功能与协议清单、构建环境 | 可复现版本、文件统计、原始构建结果 |
| 1 结构规则 | 250 行检查、历史超限清单、依赖规则、记录模板 | 新文件限制可检查，历史债务透明 |
| 2 模型与边界 | 按域移动模型、纯函数、错误和现有接口 | 不引入新行为，调用引用完整 |
| 3 源站适配 | 拆 HtmlParser、LsbClient、表单与网络协作者 | UI 可迁移到稳定 repository 边界 |
| 4 存储与会话 | store 所有权、缓存、设置观察、Session 委托 | 数据层与 UI 分离，全局状态职责收窄 |
| 5 已有切片 | 搜索、屏蔽、淘帖先统一新规则 | 形成完整的小业务迁移范式 |
| 6 普通业务页 | 板块、用户、登录、通知、私信、称号与工具页 | 无直接请求与解析，文件均合规 |
| 7 复杂编辑与设置 | NewTopic、AppSettings、Home 和相关组件 | 草稿、tab、设置与恢复责任明确 |
| 8 帖子与正文 | TopicScreen、Components、跳转、搜索、导出 | 巨型状态依赖拆解，全部生产文件合规 |
| 9 收尾 | 清除代理、未迁移调用、废弃实现；构建与文档同步 | 结构完成，准备最终实机验收 |
| 10 实机验收 | 原版对照、覆盖主要业务、修复发现的问题 | 实机记录与明确发布结论 |

### 15.1 一批任务的合理规模

一批选择一个清楚的责任，如“抽出主题投票面板 parser”，而不是“重写所有数据层”。批次包含：目标代码、受影响调用者、必要 DI 接线、已有测试源码的编译修复和文档记录。

巨大文件可以拆成多个批次，先移动低耦合模型和组件，再处理共享状态；不要为了限制 diff 大小留下一半调用者使用两套不同规则。

每批步骤：

1. 读取相关代码及全量调用者，记录不变量与当前状态归属。
2. 确定目标职责、文件和最小公开契约。
3. 移动或提取实现，保留原协议与算法。
4. 更新调用者、DI、路由和必要测试源码引用。
5. 执行行数、依赖和编译检查。
6. 审查是否新增请求、改变缓存、状态寿命或错误处理。
7. 更新迁移记录，登记待实机验证场景。
8. 建立独立版本检查点，再进入下一批。

### 15.2 每批完成定义

- 本批目标职责已迁移，新增文件和已完成文件 ≤250 行。
- 相关生产与已有测试源码编译通过；没有新增未解释的构建错误。
- 依赖方向符合规则，或明确列出尚未迁移的旧入口及下一批计划。
- 没有复制一套业务算法作为“临时新实现”长期并存。
- 兼容性清单更新，接口和状态归属可查。
- 所有未做的业务验证明确写为“未执行”，不写“回归通过”。
- 版本检查点与变更清单齐全。

### 15.3 失败与暂停条件

出现编译失败、接口矛盾、数据归属不明确、协议含义无法从代码确认或发现不可解释的行为变化时，先解决本批问题，不把破损中间态作为下一批基础。

需要源站行为证据而当前不能验证时，保留旧行为，缩小本批范围，将变更登记到实机阶段；不要猜一个接口或默认规则来凑完成。

## 16. 重构期间的非业务检查

### 16.1 必须执行

| 检查 | 发现的问题 | 不能证明 |
| --- | --- | --- |
| Kotlin 编译 | 类型、导入、接口、可见性和引用问题 | 源站数据与交互正确 |
| Debug APK 构建 | 资源、Manifest、打包和装配问题 | 实机可正常完成业务 |
| 测试源码编译 | 旧测试与新接口断裂 | 测试断言通过 |
| 行数扫描 | 超限和规避上限 | 职责划分合理 |
| 依赖扫描 | 显式跨层引用与循环迹象 | 运行时状态无竞态 |
| diff / 调用点审查 | 遗漏入口、重复算法、非预期规则变化 | 全部行为等价 |

可以使用已有 Lint 或编译器警告；新增静态工具前核对兼容性和成本。250 行检查不依赖必须安装某个插件，先用简单可复现的扫描实现即可。

### 16.2 构建任务示例

在根工程使用 Windows Gradle Wrapper。先确认当前任务实际存在，再执行：

```powershell
.\gradlew.bat :app:compileDebugKotlin
.\gradlew.bat :app:compileDebugUnitTestKotlin
.\gradlew.bat :app:assembleDebug
```

第二项只编译测试源码，不执行测试。如另有 androidTest 源集，可在环境支持时只编译其源码。

收尾执行 Release 构建并检查资源和打包。签名材料不齐全时，明确记录受阻原因和已完成的编译 / 未签名产物检查，不能以 Debug 成功冒充 Release 成功。

不使用会隐式运行测试的 `build`、`check`、`test`、`connectedAndroidTest` 或 `connectedCheck` 作为重构阶段默认入口。静态任务如有自定义依赖，先核对任务图，确保不会触发业务测试。

当前 `.github/workflows/release.yml` 包含真实发布动作，构建验收只使用本地构建任务或明确的构建流程，不能触发发布工作流充当检查。

### 16.3 依赖扫描规则

至少检查 import 和全限定引用两种写法：

- `ui/feature` 是否引用 `LsbClient`、`HtmlParser`、OkHttp、Jsoup 或偏好存储。
- `data` 是否引用 `sb.linux.client.ui` 或 Compose。
- `domain` 是否引用 Android、Compose、Jsoup、OkHttp 或 data 实现。
- 页面是否 `new` / 构造网络客户端或 store。
- 是否出现旧 Session 的已淘汰入口、复制的 parser 或万能工具类。

源站页面解析使用 Jsoup 时归 `data/parser`；UI 与 data 共用的 HTML / Markdown 文本转换归 `common/content`；使用 Compose 的正文展示处理归 `ui/common/content`。Android Context 等平台依赖必须归到允许层，不能用统一忽略规则屏蔽全 data。

文本搜索是最低限度检查，不是完整依赖证明；还需人工审查装配引用、构造依赖和跨文件状态访问。

## 17. AI 开发与交接规范

### 17.1 每次执行前

AI 应阅读本开发文档、最新进度记录、目标业务域代码及其调用者。不得只按历史架构文档的目标路径假设代码已经迁移。

确认四件事：本次边界是什么、现有行为是什么、哪些部分未验证、上次检查点是什么。

### 17.2 每次执行中

- 优先迁移现有实现，少改算法和表达式。
- 修改函数签名前搜索全部调用者，包含测试、路由和全限定类型引用。
- 增加抽象时写明实际复用点，不以设计模式名称作为理由。
- 不自行联网采集账号数据，不请求真实业务，不触发外部写操作。
- 不用“已经编译”推断“已经验证”，不编造提交号、测试结果或设备结果。
- 不生成巨大 `Utils.kt`、`Manager.kt` 或功能重复的备份实现。
- 不顺手更新依赖、改签名、改版本号或触发 Release。
- 遇到无法确认的业务语义保留原代码并记录，不猜测补齐。

### 17.3 交接必须包含

完成职责、改动文件、剩余旧入口、静态 / 编译结果、未执行业务测试、兼容性影响、实机待验项目和下一批建议。

目录、类名和行号是查找线索，行为不变量才是长期规范。进度记录必须随着代码更新，不能只在首次规划时写一次。

## 18. 全部完成后的实机测试计划

### 18.1 进入条件

进入统一实机测试前，必须完成：全范围行数合规、目标依赖关系成立、临时迁移入口清理、构建通过或明确说明环境阻塞、功能入口清单和数据兼容清单齐备。

冻结待验版本并记录版本标识与 APK 来源。保留原版 APK、可恢复的数据备份和原始配置，测试过程使用同一冻结版本；修复后记录新版本并重测受影响场景。

### 18.2 设备和安装方式

- 主设备覆盖日常 Android 版本和常用网络环境。
- 低版本环境重点检查 minSdk 26 相关平台能力；没有实际设备时记录缺口。
- 有平板布局或对应设备时验证双栏和平板导航。
- 对支持的 arm64 / armv7 产物按实际设备覆盖，不把一个 ABI 的结果写成全部通过。
- 至少验证干净安装和保留数据升级两种方式。

旧版与重构版使用相同 applicationId 时不能并装比较。使用备份、顺序安装或独立设备对照；升级版本保留原签名并满足 versionCode 要求，不通过修改 applicationId 掩盖升级兼容问题。

- 退出或切换账号后，旧请求和缓存不污染新账号。
- 长帖快速滚动、切主题、导出和返回，关注卡顿、缓存颜色和内存。
- 编辑中进入后台、取消验证或上传失败，草稿与输入保留。
- 写操作断网或超时后确认源站实际状态，避免重复提交。
- 备份导入或数据清理后，UI、设置与网络策略一致更新。

### 18.5 问题处理

记录：冻结版本、设备 / 系统、账号权限、网络环境、前置数据、操作、期望、实际、日志或脱敏截图及对应模块。

优先级：P0 为数据丢失、账号串数据、重复写操作等阻塞问题；P1 为关键功能无法使用；P2 为一般功能或交互问题；P3 为轻微表现问题。

发现问题后，修复相关责任域并重复静态 / 编译检查，再实机重测受影响路径和共享能力的主要调用者。测试期间的修复仍必须满足 250 行限制。

P0 / P1 未解决时不宣布实机验收通过。仍未覆盖的设备、网络和权限场景须保留在交付记录中。

## 19. 风险登记

| 风险 | 结构检查为何不够 | 处理要求 |
| --- | --- | --- |
| 面板被 DOM 清洗提前删除 | 编译不会检查解析结果 | 保留顺序，记录节点副作用，最终特殊帖验证 |
| 同名字段丢失 | Map 类型仍可编译 | 保留多值序列，审查全部转换路径 |
| 写请求被重放 | 编译无法证明源站是否已执行 | 保留门控与未知结果语义，最终超时验证 |
| Cookie / WebView 脱节 | 接口完整但实际会话可能失效 | 核对同步方向和生命周期，最终登录验证 |
| 状态作用域改变 | 代码合法但返回状态可能丢失 | 迁移清单、effect key 审查，最终恢复验证 |
| 旧请求覆盖新账号 | 需运行时并发触发 | 账号版本检查与任务归属，最终切换验证 |
| 设置失去可观察性 | 写盘成功不代表界面刷新 | 唯一所有者、观察链清单，最终逐域验证 |
| 正文缓存忽略主题 | 正文数据存在但颜色过期 | 保留键因素和失效，最终换主题验证 |
| 备份 / key 不兼容 | 编译无法识别历史数据 | 保留格式和读写清单，最终升级及导入验证 |
| 新类承担旧巨型职责 | 行数下降不代表复杂度下降 | 审查协作者、状态网和调用链 |
| 旧文档误导后续 AI | 路径和历史状态看似可信 | 回填真实架构，归档或标明历史规范 |
| 最后集中发现问题 | 没有阶段业务测试作定位证据 | 小批检查点、迁移映射和原行为记录 |

统一实机测试符合本次约定，但意味着行为偏差会较晚发现。因此本轮优先保留算法和协议；需要改行为的优化必须显式记录，不能借重构隐藏。

## 20. 最终完成定义

### 20.1 结构改造完成

- 所有范围内手写 Kotlin 文件 ≤250 行，历史超限清单清零。
- 页面业务状态和请求协调由页面 ViewModel 负责，通过 domain repository / use case 契约调用数据层；Screen 只负责展示与输入，Route 负责依赖取得和导航接线。验证码、Cookie / WebView、图片宿主等平台桥接须有明确边界。
- domain 保持纯净，data 不依赖 UI，循环依赖和反向全限定调用清除。
- Session 已拆为有明确所有者的会话、设置、缓存和 UI 协调组件；保留的 Session 仅作 ≤250 行的窄协调入口。
- HtmlParser 聚合门面与旧嵌套 DTO 已删除；Components 等聚合职责已实质拆解。
- 公共能力有明确语义和实际调用者，不存在新的万能基类或聚合对象。
- 数据、会话、缓存、草稿和页面状态有清楚所有者。
